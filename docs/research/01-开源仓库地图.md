### 0.2 三条选型主张

1. **骨架用 TC264-ZongZuanFeng，不自己发明。** 同为 TC264D + 逐飞库 + MT9V03X，它的 `isr_config.h` 中断分配表、`Image_Use[i][j]=&mt9v03x_image[i*2][j*2]` 零拷贝降采样、CPU0 感知/CPU1 控制双核切分可以直接搬，省掉最难调的那部分（中断优先级、核间共享、DMA 触发源）。
2. **元素判据抄 17th-SmartCar 与 HammerTa 的"结构"，不抄代码。** 两者都把元素识别写成"路线先验 + 标志互斥门 + 几何否决 + 前摇分诊"四层，而不是一堆 `if`。我们的 `MIDLine_REMAIN.c` 现在只有十字一种，照这个结构补齐环岛/三叉/坡道/车库才可维护。
3. **先做逆透视，再谈元素。** 当前最大缺陷不是缺元素，是"对整条边线做一次最小二乘直线拟合"——透视投影下弯道本来就是曲线，靠直线拟合永远不准。RUBO-UDIPM 给出了现成的查表方案（§3.12），改造量约 100 行，收益覆盖所有弯道。

### 1.2 下载通道实测（重要，后续复用）

| 通道 | 结果 |
|:--|:--|
| `git clone https://github.com/...` 直连 | `Recv failure: Connection was reset` |
| `git clone` 走 `HTTPS_PROXY=http://127.0.0.1:7890` | **只有第一次成功**，之后全部 `schannel: failed to receive handshake, SSL/TLS connection failed` |
| `raw.githubusercontent.com` 直连 | 可用（约 4.8s） |
| `gh-proxy.com/<github原始URL>` 前缀 | **最稳最快（约 1.0s）**，本次 11 个仓库全部经此下载 |
| `cdn.jsdelivr.net` / `ghproxy.net` / `kkgithub.com` | 不通 |

```powershell
curl.exe -sL --max-time 120 "https://gh-proxy.com/https://github.com/OWNER/REPO/archive/refs/heads/main.zip" -o REPO.zip   # 分支名 main/master 都要试
Expand-Archive -Path REPO.zip -DestinationPath .research_refs\REPO -Force
```

**三种哲学**（对应三种赛道特性）：
1. **全图加权平均**（本工程、wuyou33）——稳，但前瞻量不可控，进弯晚。
2. **定行取点**（xiayu）——前瞻量精确可控，但抗噪差，丢一行就崩。
3. **平方加权 + 一个"前瞻长度"旋钮**（USTB_Swan 的 `turn_height`）——把前瞻量变成一个可调参数，且权重曲线连续。**推荐折中**。

## 3. 逐个档案卡

### 3.1 USTB_Swan（北京科技大学，RT1064）

**规模**：179 文件 / 151 源文件 / 1.4MB　**编码**：UTF-8（少数 GBK）　**笔记**：`_notes/USTB_Swan.md`（约 22K 字）

| 项 | 内容 |
|:--|:--|
| 三层任务 | 1ms `sensorupdate()` / **5ms `control()`（200Hz）** / 帧率主循环产 `turn_line, turn_height, search_speed_cmd` |
| 图像 | 188×120 → **94×56**（`IMG_ZIP=2`），Otsu + `OTSU_OFFSET 7`；`IS_WHITE/IS_BLACK` 直接比 `binary_threshold`，**不生成二值图数组** |
| 边线 | 八邻域迷宫法（`search.c` 2883 行）+ `boundary_l/r[]` / `edge_l/r[IMG_H]` + 拐点表 |
| 元素 | 环 7 态 `:1439-1650`；斜十字 `:2151-2229`；坡道用陀螺 `ori_gyro_x>3500` |
| 参数 | AT24C EEPROM 7 档×256B，但**在线调参 UI 被删**（`main.c:159-162`） |


**它用"电感 + 连通域 room 数"当门控，图像只做确认**——这比纯图像判据稳得多，代价是要有 4 路电感，我们没有。

**`room` 连通域计数（`:1996-2088`）是它的核心观测量**：直道 2、环岛 4、三叉 6、十字 8。换赛道必须重标。

#### ⑥ 控制环：航向环是事件驱动，不是定时

- **TIM6 = 1 ms（速度环）**，而**航向环更新率 = 图像帧率**（`img_flag` 事件驱动）。这点很重要：**舵机没必要 200 Hz 算，图像才 50 fps**——我们现在的 5 ms 舵机有 3/4 的拍子在重复算同一个偏差。
- 舵机位置式：`kp1*e + kp2*(99-Topline)*e/1000 + ki*(e+e1+e2) + kd*(e-e1)`，`kp1=2.3 kp2=2.0 kd=6.9`。**`(99-Topline)` 加权** = 视野越短（远端被截）越保守地放大增益。
- 限幅 **±800 对称，无四象限非对称**；舵机死区 ±10、差速死区 ±50。
- 差速 = `tan(舵角)*0.396`（阿克曼几何），比我们的 `0.004*error` 线性比更接近真实转向关系。
- **速度只有 390/370/340/330/280 分段切换，无斜坡、无曲率减速**，陀螺仪全注释未用。

2. 用本工程摄像头拍一张（可临时把 `mt9v03x_image` 原图经 TFT180 或串口导出）。
3. 运行 `RUBO_UDIPM.exe`，依次完成"去畸变标定"与"四点选点逆透视"，导出下位机代码。
4. 把生成的 `cameraMatrix / distCoeffs / change_un_Mat / move_xy` 四组参数替换到 `去畸变+逆透视下位机.txt` 模板里。
5. `ImageChange_Init()` 放在摄像头初始化之后调用**一次**。
6. 把 `code/Camera_REMAIN.c` 的二值化输入从 `mt9v03x_image` 改成 `ImageUsed`，尺寸常量换成 `RESULT_ROW/RESULT_COL`。
7. **RAM 核算**：指针表 `100×114×4 = 45.6 KB`。TC264 的 DSPR 不够奢侈时，改存 `uint16_t` 偏移（`y*188+x`，最大 22559 < 65535）→ **22.8 KB**，取像素时 `mt9v03x_image_dvp_flat[offset]`。

**注意**：`cameraMatrix/distCoeffs/change_un_Mat` 是**那台车的位姿专属值**，直接抄会得到错误的坐标映射——必须用自己的标定照重新生成。

## 5. 选型结论

### 5.1 骨架选谁

```
硬件/中断/双核/降采样     ← TC264-ZongZuanFeng（同平台，逐引脚对应）
图像预处理 + 逆透视       ← RUBO-UDIPM 查表模板
边线提取（八邻域，可选）  ← SmartCarBaseCameraByXiayu
补线一致性                ← wuyou33 的"画回二值图再重爬"
中线加权 / 前瞻旋钮       ← USTB_Swan 的 line²+1 + turn_height
元素状态机                ← 17th-SmartCar 的四层结构 + HammerTa/losehu 的阶段拆解
控制环                    ← 本工程现有实现 + USTB_Swan 的四象限限幅 + 1:25 斜坡
参数与调试                ← smartcar2022 Flash 参数块 + RT1064 SerialIO
```

### 5.2 三条不要做的事

1. **不要抄 wuyou33 的 PID**：`MotorPID_Output` 没有累加器，名为增量实为纯 P。它的**元素状态机**值得抄，**控制器**不值得。
2. **不要抄 smartcar2022 的 `imgproc.c`**：633 行八邻域巡线库是死代码，从未接线跑过，其中的行号和参数都不是实车验证过的。
3. **不要抄 xiayu 的补线 A 策略**：写 `image[y][key]=2` 而不写 `Left_Line[]`，对控制零影响——会让人误以为补线生效了。

### 5.3 下一步（详细改造清单见 `03-改造清单.md`）

| 优先级 | 事项 | 参考 | 预期收益 |
|:--:|:--|:--|:--|
