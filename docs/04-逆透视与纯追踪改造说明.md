## 0. 一句话总结

原来的控制链是「全局 Otsu → 逐行找边 → **一条最小二乘直线** → 全图加权平均中线 → 偏差 → 分段 Kp 打角」。
弯道上直线拟合会偏离真实边线，全图平均又把远场（真正的转向信息）和近场一起平均掉，所以**弯道只能靠"误差变大→多打角"事后追**，路口更是直接强行回正。

这一轮做了两件事：

1. **把图像逆透视成俯视图**（56×96，1 格 ≈ 6.7 mm × 11.8 mm），赛道在图上变成真正的「两条平行边线」，宽度、横向偏移、曲率都有了物理量纲；
2. **用纯追踪（Pure Pursuit）算转向**：在俯视图上按当前速度选一个前瞻点，用几何关系算出需要的转弯曲率 κ，再换算成前轮转角 δ 和舵机占空比——**这是"预瞄"，不是"追误差"**。

外加两个针对你特别提到的痛点做的专项保护：

- **十字路口四层判据**（互斥门 → 几何否决 → 状态机 → 出路口防重触发），过路口时**沿进路口前的航向直行**，绝不跟随横臂；
- **弯道不误判路口**、**冲出赛道检测**、**视野丢失时保持上一份控制量 5 帧**。

## 2. 逆透视（IPM）

### 2.1 为什么不用别人的标定矩阵

参考仓库（losehu/smartcar-C、wu58430/RUBO-UDIPM）里都是**硬编码一份 3×3 单应矩阵**，那是别人车、别人相机安装角标出来的。装到你车上必定错位。

所以这里的做法是：**用参数化的针孔模型自己生成查表**，把「相机高度 / 俯角 / 水平视场角」三个物理量变成宏，改宏就重新生成，不需要上位机、不需要标定板。

### 2.2 推导

车辆坐标系：**X 向右、Y 向前、Z 向上**，原点在车头正下方地面。相机装在 `(0, 0, h)`，光轴向下俯 `θ`。

相机坐标系三轴（相机 y 朝下、z 朝前）：

```
x_c = (1, 0, 0)
y_c = (0, -sinθ, -cosθ)
z_c = (0,  cosθ, -sinθ)
```

地面点 `P = (X, Y, 0)`，相对相机的向量 `P - C = (X, Y, -h)`，投影到相机坐标：

```
x_c = X
y_c = Y·(-sinθ) + (-h)·(-cosθ) = h·cosθ − Y·sinθ
z_c = Y·cosθ  + (-h)·(-sinθ)    = Y·cosθ + h·sinθ
```

针孔成像（像素坐标以像素中心为原点，`cx = W/2 − 0.5`、`cy = H/2 − 0.5`）：

```
u = cx + f · x_c / z_c
v = cy + f · y_c / z_c
f = (W/2) / tan(FOV_H / 2)
```

地平线（`Y → ∞`，此时 `v = cy − f·tanθ`）与 `z_c` 的正负决定了哪些像素是天空——天空行的查表项一律写 `IPM_LUT_INVALID`。

### 2.3 实测数值（v = 78.875 px、地平线 = 27.63 行）

`W=188, H=120, h=240 mm, θ=22°, FOV_H=100°`：

| 图像行 v | 对应地面 Y | 该处 1 像素 ≈ |
|---|---|---|
| 119（最下沿） | 144 mm | 2.8 mm |
| 110 | 170 mm | 3.5 mm |
| 100 | 207 mm | 4.6 mm |
| 90 | 256 mm | 7.0 mm |
| 80 | 324 mm | 11.5 mm |
| 70 | 423 mm | 20 mm |
| 60 | 583 mm | 35 mm |
| 50 | 888 mm | 70 mm |
| 40 | 1684 mm | 240 mm |

**结论：图像底行只覆盖 144 mm，图像 40 行以下已经是 1.7 m 开外、每像素 24 cm。**
所以俯视图取 `Y ∈ [150, 800] mm`——最下沿刚好不浪费，最远处 1 像素仍有 30 mm 分辨率。再远（>900 mm）单像素 45 mm 以上，边线宽度和噪声同量级，取进来只是噪声。

### 2.4 网格与查表

```c
IPM_H = 64, IPM_W = 96
Y_NEAR = 150 mm, Y_FAR = 1400 mm, X_HALF = ±320 mm
→ DX = 6.74 mm / 格, DY = 19.84 mm / 格
→ 出界格点 39 / 6144 = 0.6%（越界填白，等于赛道两侧自动留白）
```

> **为什么从 800 mm 加到 1400 mm**：800 mm 时俯视图最高一行只对应源图第 52 行，路口一挡，
> 画面下半截就没信息了，`above_rows`（中断带"上方"又看清的行数）永远是 0 —— 等于"看不出路面
> 有没有回来"，路口判据的第一层直接失效。1400 mm 对应源图第 42 行（Y=1100 mm 是第 46 行），
> 路口挡住 500~760 mm 时，760~1400 mm 那段还能看见白路面，`above_rows` 才数得出来。
> 代价只是 DY 从 11.8 mm 变成 19.8 mm（前瞻点取 3 行平均，已经把这点量化误差压掉）。

`IPM_Init()` 逐格算一次 `(u, v)`，存成 `uint16 ipm_lut[64][96]`（内容是 `v*188 + u` 的一维偏移，越界存 `0xFFFF`）。
运行时 `IPM_Process()` 只做 6144 次「读偏移 → 取像素 → 写目标」，**没有一次浮点运算**。

内存：LUT `64*96*2 = 12.0 KB`，俯视图 `64*96 = 6.0 KB`，合计 ≈ 18 KB。
（对比 losehu 用 `uint8*` 指针表 45.6 KB——同一个思路，这里用 `uint16` 偏移省了 3/4。）

> 相关宏：`IPM_CAM_HEIGHT_MM`、`IPM_CAM_PITCH_DEG`、`IPM_CAM_FOV_H_DEG`。改这三个值会重建整张表。`IPM_Init()` 末尾有自检：出界格点超过 1/4、或地平线跑出画面，就置 `ipm_info.ok = 0`，纯追踪自动退回老算法。

## 3. 纯追踪（Pure Pursuit）

### 3.1 找边界（`pursuit_find_floor`）

**这个赛道的边界不是黑线，而是"白路面 → 暗地板"的跳变**（白胶带铺在蓝色地板上）。所以算法不是"找黑色几何中心线"，而是"找路面消失的地方"：

- 以画面中线 `47.5` 为起点，从最近一行（r=0）往最远行逐行扫；
- 用上一行的中线预测本行位置 `pred = pc + slope`（斜率跟踪弯道趋势，且夹在 ±`PURSUIT_SLOPE_MAX`);
- 以 `pred` 为起点向左右各扫最多 `PURSUIT_SEARCH_COLS = 42` 格：
  - 遇到**细暗条纹**（连续暗格 ≤ `PURSUIT_LINE_W_MAX = 8`，即斑马线/横臂/反光缝）→ **跳过，继续往外扫**；
  - 遇到**第一段够厚的暗区**（连续暗格 > 8）→ 认定踩到地板，取该暗区**内侧第一个格子**为边界列；
- 两侧都在、宽度落在 `[22, 92]` 格、且与学习到的赛道宽度相差不到 50% → **可信行**，同时缓慢学习半宽 `hw` 与斜率；
- 两侧都在但宽度 > 学习宽度 × `PURSUIT_WIDE_RATIO(1.45)` → 记为 **wide 行**（横向支路开口），中线沿航向外推；
- 只有一侧 → 用学习到的半宽推算另一侧，但推算点离预测位置不得超过 `PURSUIT_SINGLE_TOL(10 格)`，否则降级为外推；
- 两侧都没有 → 沿预测方向外推（`center = pred`），**绝不去跟横臂、也绝不跟着支路拐**；
- **第 0 行特殊处理**：车头正下方那一行只校验宽度是否落在 `[22,92]` 格，不做突跳/半宽一致性校验，并直接用它把 `hw`、`pc` 复位。否则赛道只要比初值窄一点、或者车起步时偏了 5 cm，整帧都判不出可信行。

**为什么不能用"黑游程中点"**：蓝色地板整片都是暗的，那种写法会把整片地板当成一条边线，返回地板正中间（仿真里 29..66 的路返回 14.0、厚度 29），厚度永远 > 8 格 → 每行两侧全被判丢 → `valid = 0` → **纯追踪永远不生效，车一直跑的是老 PD**。这是本次实车"路口右冲"的第一层根因。


### 3.2 前瞻距离随速度变化

```c
norm = control_base_speed_ref / CONTROL_SPEED_MAX      // 规划速度，不是实测速度
norm = clamp(norm, 0.30f, 1.0f)
Ld   = 250 + (800 - 250) * norm                        // 250 ~ 800 mm
r0   = (Ld - 150) / dy                                  // 换算成俯视图行号
```

`control_base_speed_ref` 必须是**第 6 步算出来的规划速度**，不能用编码器实测速度——否则「减速 → 前瞻变近 → 打角变大 → 更减速」会形成正反馈。

用规划速度还有一层好处：**减速和预瞄自动配套**。弯里慢下来 → 前瞻点自动拉近 → 打角更狠，正好符合"慢进快出"。

### 3.3 曲率 → 转角 → 舵机

目标点（对 `r0-1 / r0 / r0+1` 三行取平均，抑制单行噪声）：

```c
Xt = (cc - 47.5) * dx_mm          // 横向偏移，右为正
Yt = 150 + r0 * dy_mm             // 前向距离
κ  = 2·Xt / (Xt² + Yt²)           // 圆弧过原点和目标点的曲率
δ  = atan(κ · L)                  // 前轮转角，L = 130 mm 轴距
```

舵机（这一步的正负号最容易错，这里写清楚；实车已确认最终版）：

```
实车实测极性：占空比小 = 前轮向右，占空比大 = 前轮向左（中值 460）
Servo_Set_Offset() 里：out 正 = 向右打，duty = Servo_MID + (SERVO_DIR)·out，SERVO_DIR = −1 → 占空比减小
纯追踪里：δ 正 = 右转
所以：steer = +(δ / δ_max) · SERVO_DUTY_RANGE_L     // 不取负号
      并按 [−RANGE_R, +RANGE_L] 非对称限幅（向右 65 码 / 向左 74 码）
```

> 早期版本这里多写了一个负号（`steer = −(δ/δ_max)·RANGE_L`），实车表现为「左弯往右打」，
> 已在 §8.6 里记录并修正。判断极性有一个免费证据：老 PD 通路 `duty = MID − out`，
> `error>0`（赛道偏右）时占空比变小而车确实在往右走 —— 说明「变小 = 向右」。

仿真验证过符号：右弯 `κ>0 → δ>0 → steer>0 → duty 减小 → 向右` ✓；左弯反之 ✓。

### 3.4 差速与减速

```c
ratio = κ_use · REAR_TRACK / 2                        // 纯几何：内侧轮慢多少
      clamp ±CONTROL_DIFF_K_MAX (0.5)
slow  = 1 − 0.014 · |δ_deg|                           // 32° 满舵 → 0.55，再 clamp ≥ 0.42
```

`ratio` 与原来的 `CONTROL_DIFF_K * error` 同号（正 = 左轮快 = 右转），所以 `target_l = base·(1+ratio)`、`target_r = base·(1−ratio)` 这两行完全不用改。

原来的线性近似 `ratio = 0.004 × error` 是"像素偏差乘一个系数"，量纲说不清；现在是 `κ·轮距/2`，物理上就是内外轮的速度差比例。

## 4. 十字路口（四层判据）

这是本次的重点，按你提的"路口容易冲出去"专门设计。**判路口最难的不是"看出它是路口"，而是"别把弯道当路口"**。

### 第一层：先量出三种"行"

| 行类型 | 含义 | 怎么来的 |
|---|---|---|
| **可信行** `valid_rows` | 左右边界都在，宽度和学过的宽度一致 | 中线可以直接用 |
| **wide 行** `wide_rows` | 左右都找到了，但宽度一下子大了 45% 以上 | 横向支路开口，中线沿航向外推 |
| **open 行** `open_rows` | 两侧同时找不到足够厚的暗区 | 路面"变白消失"或整行丢失 |
| **one-side 行** `one_side_rows` | 只有一侧在 | 半宽推算，但推算点必须靠得住 |
| **标记行** `mark_rows` | 路面里横着 2 段以上的**黑色短横条** | 一行里数短暗条的段数（`pursuit_count_marks`） |

### 第二层：中断带 + 上方回看（这是判路口的核心）

```c
band_rows  = 第一段连续不可信行的长度          // 路面"断掉"的那一段有多长
above_rows = 这段不可信行"上方"又看清的行数     // 路面"回来了"多少行
```

| 场景 | band | above | 判定 |
|---|---|---|---|
| 直道 / 窄道 | 0 | 0 | 都不是 |
| **十字路口（单侧开口）** | **14** | **16** | **路口** |
| **十字路口（两侧开口）** | **14** | **16** | **路口** |
| 弯道 R=400 | 27 | **0** | **弯道** |
| 弯道 R=250 | 33 | **0** | **弯道** |

→ **一句话：路面"消失一段又回来"是路口，"消失后再也不回来"是弯道。** 这比任何宽度阈值都稳，因为它是拓扑特征，不依赖标定。

判据：

```c
suspect = (band >= PURSUIT_CROSS_MIN_BAND(4) && above >= PURSUIT_CROSS_MIN_ABOVE(4))
       || (wide_rows >= PURSUIT_CROSS_MIN_WIDE(5))
       || (open_rows >= PURSUIT_CROSS_MIN_OPEN(6) && open_rows > one_side * 3 / 2 && above >= 2);

// 判据零（放在所有否决之后、带否决权）：路面上的黑色短横条标记
if(mark_rows >= PURSUIT_MARK_MIN_ROWS(2)) suspect = 1;
```

**判据零为什么最硬**：实车视频里这个赛道的十字路口，是在白路面上横贴**两排黑色短横条**（斑马线样式），
路面本身继续往前。横条厚度只有 1~2 格，`pursuit_find_floor()` 会把它当"路面内的细暗条纹"跳过
（所以左右边界照样找得对），但一行里能数出 ≥2 段这样的短暗条 —— **弯道永远数不出这个特征**
（弯道外侧是一整片连续地板，不构成短暗条）。所以它一旦成立就认定路口，不管 `κ_prev` 之类的否决怎么说。

四条否决（任一条成立就不判路口）：

```c
(wide + open) > IPM_H * 3 / 5          // 大半个画面都没了 = 摄像头/光照问题
valid < PURSUIT_CROSS_MIN_VALID(8) && above < PURSUIT_CROSS_MIN_ABOVE(4)   // 看得太少且不是路口
|κ_prev| > PURSUIT_CROSS_MAX_KAPPA(0.0025)   // 进路口前车头正在大转弯 = 它本来就是弯道
cross_reject > 0                        // 刚出路口，防抖
```

最后一条 κ 否决仍然是关键：**急弯的 band 也很长（27~33 行），但它 above 恒为 0**，所以两条判据互相兜底。

### 第三层：状态机（IDLE → IN → OUT）

```c
连续 2 帧 suspect → 进入路口，cross_ticks = 32（0.64 s ≈ 640 mm）
路口内：
    cc  = 第 1~8 行（车头前 170~310 mm）里所有可信行的中线平均   // 只看脚下的车道轴
    yt  = PURSUIT_CROSS_LOOKAHEAD_MM (400)                    // 前瞻固定 400 mm
    κ   = 2·xt / (xt² + yt²)                                  // 只有横向纠偏，没有转弯
    Δ 夹 ±PURSUIT_CROSS_DELTA_MAX (6°)                         // 就算偏 200 mm 也只给 6°
    还在路口里（suspect 成立）就 cross_ticks 续期             // 车慢也不会中途退出
    slow × CONTROL_CROSS_SPEED_SCALE (0.80)
路口内不做"可信行不够就交回老 PD"的降级 —— 老 PD 会跟着被支路拉走的中线往左右拐
退出：连续 8 帧干净（cross_clean >= 8）或 cross_ticks 用完
出路口后 cross_reject = 20 帧禁止再判 —— 防"刚出路口又判路口"来回抖
```

**过路口为什么"沿近场车道轴直行"**（这是第二版改动，第一版是"保持进路口前的 κ 并衰减"）：

1. 你提的要求是**路口只能直行，不许左拐也不许右拐**。保持进路口前的 κ，本质是"车头斜着进来就斜着出去"，
   万一进路口那一帧已经被支路拉歪了，整条直线就是歪的；
2. 近场（车头前 170~310 mm）永远是脚下的真路面，横向路再宽也挡不住它。用它当前瞻参考点 +
   前瞻距离固定 400 mm，等价于"以脚下这段车道为轴、笔直往前开"，横向偏了会自动纠回轴线上；
3. 反向效果也安全：万一车头已经歪了 5°，这条规则会在 400 mm 内把它拉回车道轴，而不是顺着歪方向走。
   再配上 Δ ≤ 6° 的硬限幅，物理上不可能在路口里拐进左右支路。

> 第一版还有一个隐患，第二版一并修掉了：进路口前的 MIDLine 把 `error` 强行置 0（"回正"），
> 等于让舵机突然回中，车顺着斜航向直冲路口四角 —— 那是"冲出去"的头号元凶。

所以 `code\MIDLine_REMAIN.c` 的路口分支也一起改成了"保持上一帧中线"：

```c
midline_info.center         = midline_info.last_mid_line;
midline_info.mid_line_value = (uint8)(midline_info.last_mid_line + 0.5f);
midline_info.error          = midline_info.last_mid_line - (MT9V03X_W * 0.5f);
```

### 第四层：可信行前瞻 + 物理保护

纯追踪的目标行不是"盲目取前瞻距离对应的行"，而是**从该行往下（往近处）找第一个左右都可信、且上下相邻也可信的行**。路口里那些 wide/open 行永远不会被选成目标行 —— 前瞻点因此永远落在"真路面上"，而不是支路里。

再叠两道物理保护：

- 路口内 Δ 夹 ±6°（见上，`PURSUIT_CROSS_DELTA_MAX`）；
- `Servo_Set_Offset()` 里有 `SERVO_SLEW_MAX = 14`（每 5 ms 最多变 14 个占空比，69 打满要约 25 ms），舵机不会因为一次误判瞬间甩到极限。

## 6. 视野丢失时保持 5 帧（防止弯中抖动）

```c
if (trk_valid < PURSUIT_CROSS_MIN_VALID)      // 可信行 < 8
{
    if (pursuit_hold < PURSUIT_HOLD_FRAMES)   // 5 帧 = 100 ms
    {
        pursuit_hold ++;
        snap = 上一份快照;                     // 原样继续用，只更新统计字段

}

```

没有这一段的话，一帧反光/抖动就会让 `valid` 变成 0，控制权瞬间交给老的分段 Kp 控制器——两套控制器输出差得远，车就会在弯中"抖一下"。这也是纯追踪必须配的东西：**两套算法的切换必须是"渐进的"或"有滞回的"，不能逐帧硬切。**

`Servo_Set_Turn()` 里也加了对应的无扰切换：从纯追踪切回偏差打角时，先把 `servo_err_f` 和 `servo_last_error` 同步成当前误差，否则微分项 `SERVO_KD * (error − last_error)` 会猛跳一下。

**第 3 步：确认舵机行程与打角极性**

舵机实测：中值 **460**、50 Hz、可用占空比 **395 ~ 534**。这三个数已经写进 `code\Servo_REMAIN.h`：

```c
#define Servo_MID      (460)
#define SERVO_DUTY_MIN (395)     // 机械下限，谁也不许越过
#define SERVO_DUTY_MAX (534)     // 机械上限
#define SERVO_DIR      (-1)      // 打角极性，见下
```

- `SERVO_DUTY_MIN/MAX` 是**唯一**的行程来源：`Servo_Set_Duty()` 直接夹这两个数，`SERVO_DUTY_RANGE_L/R` 也由它们推导（向下 69 个码、向上 70 个码）。所以偏差 PD、纯追踪、出弯保持三条路径**都不可能**把占空比推出 395~534，不存在"某条通路忘了限幅"的情况。
- **打角极性标定**（必做，5 秒）：上电、车轮离地，临时在 `Servo_Init()` 末尾加 `Servo_Set_Duty(400);` 看前轮往哪边偏，再改成 `Servo_Set_Duty(530);` 看另一边。
  - 若 **400 偏左、530 偏右** → 把 `SERVO_DIR` 改成 `(+1)`；
  - 若 **400 偏右、530 偏左** → 保持 `SERVO_DIR (-1)`（仓库原有方向）。
  这个符号同时作用于偏差通路与纯追踪通路，改一处两条一起翻，不会出现"一条通路反、一条正"的错位。**不要**再用 `SERVO_REVERSE` 调极性——它只翻偏差通路。
- 然后把 `PURSUIT_DELTA_MAX_DEG` 改成实测的**最大前轮转角**（打死方向，量角器或几何测量）。它必须和 `SERVO_DUTY_RANGE_L`（默认 69 个码）对应同一物理极限，否则 `δ` 与占空比不成比例——**这一条最容易忘，也最影响手感**。

**第 4 步：低速试跑**

`CONTROL_BASE_SPEED` 先降到 **40**，`CONTROL_SPEED_MAX` 降到 **60**（保证 `norm` 在前瞻距离的中段）。
看 `P`（可信行数）是否稳定在 40 以上；`b`（中断带长度）在直道上应为 0~2，`A`（中断带上方可信行）也应为 0，`W`（wide 行）为 0，`M`（黑条标记行）为 0。若直道上 `W` 或 `b` 经常非零，说明提取器把反光/接缝当成了地板，调 `PURSUIT_LINE_W_MAX` 或提高 Otsu 阈值下限；若直道上 `M` 非零，说明地面上真有短暗条纹，把 `PURSUIT_MARK_MIN_RUNS` 从 2 提到 3。

**第 5 步：逐项加压**

1. 先跑直道 → 确认 `d` ≈ 0，车不蛇行；
2. 再跑单弯 → 确认 `c` 始终为 0（**弯道不许判成路口**）；
3. 再跑十字 → 确认 `c` 变成 1、`M` ≥ 2、`d` 稳定在 ±6° 以内，车是"直穿"而不是"拐弯"；
4. 最后加环岛/斑马线 → 斑马线原来那套 `Zebra_REMAIN` 起停逻辑不受影响（它只看 `base_image`）。

### 8.1 首次编译踩到的坑：头文件循环 include（已修）

ADS 报 `Pursuit_REMAIN.h 97/33 undeclared identifier "IPM_H"` / `expression must be constant`，根因不是漏写宏，而是**本工程头文件的组织方式**：

```
IPM_REMAIN.c
 └─ #include "IPM_REMAIN.h"      ← 守卫 CODE_IPM_REMAIN_H_ 置位
     └─ #include "zf_common_headfile.h"
         └─ 用户层 … → #include "IPM_REMAIN.h"   ← 守卫已置位，整个文件被跳过（宏还没定义！）
                     → #include "Pursuit_REMAIN.h"
                         └─ extern int16 pursuit_center_row[IPM_H];   ← IPM_H 还不存在 → 报错
```

也就是说：**任何用户层头文件里，只要用到"排在自己后面"的头文件定义的宏，就会踩这个坑**（而单独编译那个头文件的 .c 时反而正常，所以肉眼看代码看不出来）。

修法：`Pursuit_REMAIN.h` 里的 `extern int16 pursuit_center_row[IPM_H];` 改成 `extern int16 pursuit_center_row[];`（不完整数组类型的 extern 声明合法，定义处仍是 `[IPM_H]`，链接期一致），从此两个头文件之间没有宏依赖。

**以后写新头文件的规矩**：头文件里只用「本文件自己 `#define` 的宏」+「`zf_common_*` / 驱动层符号」，不要用别的用户层头文件的宏；确实要共享常量，就写进那个宏所属的头文件，或者用 `[]` / 显式长度。

### 8.2 实车第二坑：屏幕 assert 在 `zf_device_tft180.c:460`（已修）

实车屏幕上打出：

```
Assert error
file: zf_device/
zf_device_tft180.c
line: 460
```

`zf_device_tft180.c:460` 是 `tft180_show_char()` 里的 `zf_assert(x < tft180_width_max);`——**x 越界**，不是数据错。

根因：原 `Pursuit_Show_On_TFT180()` 写了 `tft180_show_float(96, CAMERA_INFO_Y2, kappa*1000, 1, 2)`。逐飞这个函数**不按实际数字长度渲染**，而是先把缓冲区按定长补满空格：

```c
memset(data_buffer, 0, 17);
memset(data_buffer, ' ', num + pointnum + 2);   // 定长：1 + 2 + 2 = 5 个字符
func_double_to_str(data_buffer, dat_temp, pointnum);   // 只覆写前几位，末尾空格不写 NUL
tft180_show_string(x, y, data_buffer);                 // strlen = 5，而不是数字的真实长度
```

也就是 `strlen` 恒等于 `num + pointnum + 2 = 5`（`func_double_to_str` 不在数字末尾补 NUL，尾部空格被一起画出来）。屏幕是默认竖屏 **128 宽**（`tft180_set_dir(TFT180_PORTAIT)` → `tft180_width_max=128`）、字体 **8×16**，于是 5 个字符的落点是 `96 / 104 / 112 / 120 / 128`——**最后一个字符起点正好 128**，`show_char` 内部断言 `x < 128` 直接失败。因为长度是定长补齐的，**跟数值大小无关，第一帧必死**，所以表现成"上电就停在 assert 画面"。

（`tft180_show_int(x,y,dat,num)` 同理：`memset(data_buffer,' ',num+1)` + `func_int_to_str` 不补 NUL ⇒ `strlen` 恒为 `num+1`。）

修法（三处）：

1. `Pursuit_Show_On_TFT180()` 整体重排：位置改到第 7/8 行（`y = CAMERA_INFO_TOP + 100 / +116`），所有字段按 `num`/`pointnum` 的实际定长留格子（最右到 `x=127`），并加 `if((y + 16) > tft180_height_max) return;` 的兜底；
2. `IPM_Show_On_TFT180()` 从 `(0,0)` 改成**底对齐** `(0, tft180_height_max - IPM_H)`（96×56 落在 `y=104~159`），不再盖住上面六行；
3. 新增编译开关 `PURSUIT_DIS_EN`；`IPM_DIS_EN=1` 时第 7/8 行自动让位（`#if ((1 == PURSUIT_DIS_EN) && (0 == IPM_DIS_EN))`）。

**通用教训（本工程后续加任何屏幕输出都要遵守）**：

| 函数 | 渲染长度（字符数） |
|---|---|
| `tft180_show_string(x,y,str)` | `strlen(str)` |
| `tft180_show_int(x,y,dat,num)` | 定长 `num + 1` |
| `tft180_show_float(x,y,dat,num,pointnum)` | 定长 `num + pointnum + 2` |

必须满足 `x + 8 × 长度 ≤ 128`（竖屏 8×16 字体）；横屏（`TFT180_CROSSWISE`）是 160 宽、128 高，`y + 16 ≤ 128`。

### 8.3 实车第三坑：路口右冲（纯追踪其实一直没生效）

**现象**：视频里车在距十字还有三四十厘米时车头就往右偏，进路口后顺着支路开走。

**根因有两层，第一层比第二层更致命**：

1. **边界语义搞错了。** 本赛道边界是"白路面 → 暗地板"的跳变，我最初却按"找一条黑色细线"写的 `pursuit_find_run()`：它找暗游程的**中点**。蓝色地板整片都是暗的，于是它把整片地板当成一条边线的内部，返回地板正中间（仿真：一条 29..66 的路返回 `14.0`、厚度 `29`），厚度恒 > `PURSUIT_LINE_W_MAX = 8` → 每行两侧全被判丢 → `valid_rows = 0` → `Pursuit_Get()` 返回 0 → 控制层一直走 `else` 分支跑老 PD。**也就是说：加进工程的那套纯追踪，在实车上从来没有真正接管过。**
2. **就算提取器正常，路口行也会把前瞻点拽进支路。** 横向支路一开口，一侧边界瞬间远移，中线取中点就整体平移，前瞻点落进支路 → κ 变大 → 往支路拐。

| 行分类：valid / wide / open / one-side + `band_rows` / `above_rows` | 同上 | 把"路口"和"弯道"按拓扑分开 |
| 可信行前瞻（从目标行往下找 3 行连续可信） | `Pursuit_Process()` | 前瞻点永远落在真路面上，不落进支路 |
| 路口内 Δ 夹 ±8° | 同上 | 判错也不会横着拐进支路 |
| TFT 第 8 行改为 `b`/`A`/`W` | `Pursuit_Show_On_TFT180()` | 实车上能直接看出为什么判/不判路口 |

| 路口判据 | band+above / wide / open | 再加**判据零：黑色短横条标记**（`mark_rows`） | 这个赛道的路口就是两排黑横条，最硬的正面特征，弯道不可能有 |

| 路口内打角 | 保持进路口前的 κ 并衰减 | **只跟近场车道轴**（1~8 行平均，`yt=400mm`） | 你的要求：路口只能直行 |
| 路口内 Δ 限幅 | ±8° | **±6°** | 更死的直行 |
| 路口计时 | 20 帧（0.4 s） | 32 帧（0.64 s）+ **在路口内续期** | 车慢时 0.4 s 开不出路口，中途退出就又跟着支路走 |
| 路口内降级 | 可信行不足 → 交回老 PD | **路口内一律不降级** | 老 PD 正是被支路拉走的那条路 |
| 屏幕 | 第 8 行 `b` `A` `W` | 再加 `M`（黑条标记行数） | 一眼看出路口有没有被认出来 |

### 8.5 实车第五坑：连续打角在实车上"打着打着就过头"（分档打角）

现象（用户 m01708）：路口还是往右拐；弯道打角过大、容易转过头。

根因两条：

1. **连续量在实车上不可控**。`Servo_Set_Turn` / `Servo_Set_Offset` 输出的是连续占空比（437、438、439…），
   而实车舵机 + 连杆有空程、回中力不均，连续量落在"打了但不够"和"打过"之间时，车会来回修，
   修到最后就是转过头。离散档位把"这个量到底算打大还是打小"这件事从舵机手里拿回到代码里。
2. **路口的打角还是"跟目标点算出来的"**。只要远区被判可信，目标点就有可能落在支路里。
   所以路口必须有一条**与算法无关的硬规则**：直接 460，不看任何目标点。

改法（`Servo_Set_Step()`，见 `code/Servo_REMAIN.c`）：

| 档位 | 占空比 | 什么时候用 | 退出条件 |
|---|---|---|---|
| 中位 | **460** | 直线、路口（`force_center`） | `\|需求\| ≥ 1.50°` |
| 小右 | **440** | 直道调姿（需求向右 1.5°~3.5°），占空比 −20 | `\|需求\| < 0.90°` 回中、`≥ 3.50°` 升大档 |
| 小左 | **474** | 直道调姿（需求向左 1.5°~3.5°），占空比 +14 | 同上 |
| 大右 | **418** | 一般弯道（需求向右 3.5°~10°），占空比 −42 | `\|需求\| < 2.20°` 降小档、`≥ 10°` 升超大档 |
| 大左 | **500** | 一般弯道（需求向左 3.5°~10°），占空比 +40 | 同上 |
| 超大右 | **400** | 急弯（需求向右 ≥ 10°），占空比 −60 | `\|需求\| < 7.00°` 退大档 |
| 超大左 | **530** | 急弯（需求向左 ≥ 10°），占空比 +70 | 同上 |

三条保护：

- **滞环**：进档阈值和退档阈值不同（1.50/0.90、3.50/2.20、10.0/7.0），需求在阈值附近抖不会来回打档；
- **停留**：每次换档至少保持 `SERVO_STEP_DWELL_TICKS = 1` 拍（5ms）——急弯要跟得上，所以只留 1 拍，抗抖主要靠滞环；
- **路口硬回中**：`Servo_Set_Step(demand, force_center=1)` 立刻 460，清空档位状态、清出弯保持，
  **不受停留时间限制**。`Control_Tick` 第 3 步里，只要"纯追踪说路口"或"老算法说路口"任意一个成立，
  就 `force_center = 1` —— 这是"十字路口一定直行"的最后一道保险。

需求从哪来：纯追踪可信时用 `control_ps.delta_deg`（几何量，直接是度）；纯追踪不可信时用
`error * CONTROL_ERR_PX_TO_DEG`（0.60 度/像素），两条路都满足"正 = 向右"。

仿真（`%TEMP%\ssim3.py`，等价复刻 C 里的判档逻辑）：

```
直道 稳态抖动           460x24                          全在中位，不抖
直道 偏右后纠回         440x8 -> 460x3
直道 偏左后纠回         474x8 -> 460x3
一般弯 需求 4->7        460x1 -> 440x1 -> 418x4           进大档（-42）
急弯 需求 8->16         440x1 -> 418x3 -> 400x3          进超大档（-60）
急弯 左 -8->-16         474x1 -> 500x3 -> 530x2          进超大档（+70）
出弯 16->0              400x5 -> 418x3 -> 440x1 -> 460x1
路口（不给 force）      460x2 -> 400x4 -> 440x1          ← "路口会拐"就是这么来的
路口（force_center）    460x6 -> 440x1                  基本全程中位
阈值抖动 1.4/1.6        460x24                          滞环生效，不来回打
```

第 7 行是关键：**路口如果不给 `force_center`，需求 8~9.9° 会直接进 418（大右档）**，
所以"识别到路口"这件事必须同时驱动舵机回中，不能只用来减速。

新增/修改的宏（都在 `code/Servo_REMAIN.h`）：

```c
#define SERVO_STEP_EN           (1)      // 0 = 退回连续打角
#define SERVO_STEP_DIR          (1)      // 若实测"档位方向反了"，改成 -1（只翻档位，不影响连续通路）
#define SERVO_DUTY_MID          (Servo_MID + SERVO_TRIM)   // 460
#define SERVO_DUTY_R_SMALL      (440)    // 向右小档（占空比 −20）
#define SERVO_DUTY_L_SMALL      (474)    // 向左小档（占空比 +14）
#define SERVO_DUTY_R_BIG        (418)    // 向右大档（占空比 −42）
#define SERVO_DUTY_L_BIG        (500)    // 向左大档（占空比 +40）
#define SERVO_DUTY_R_HUGE       (400)    // 向右超大档（占空比 −60）
#define SERVO_DUTY_L_HUGE       (530)    // 向左超大档（占空比 +70）
#define SERVO_STEP_SMALL_IN     (1.50f)  // 进小档
#define SERVO_STEP_SMALL_OUT    (0.90f)  // 退小档（回中位）
#define SERVO_STEP_BIG_IN       (3.50f)  // 进大档
```

调参建议（按现象对号）：

| 现象 | 改哪个 |
|---|---|
| 弯道转过头 | 把 `SERVO_STEP_BIG_IN` 从 6.00 提到 8.00（大档晚一点进）；或把 `CONTROL_BASE_SPEED` 降 10 |

| 直道左右摆 | 把 `SERVO_STEP_SMALL_IN` 从 1.50 提到 2.00；`SERVO_STEP_SMALL_OUT` 保持 0.80 |
| 档位方向反了 | `SERVO_STEP_DIR` 改 -1 |
| 想彻底关掉分档对比 | `CONTROL_STEP_STEER_EN` 或 `SERVO_STEP_EN` 改 0 |

路口识别这次又补了一条判据（`trk_white`，见 `code/Pursuit_REMAIN.c`）：

- **整行全白**：俯视图里一整行 96 格**一个暗点都没有**。白路面铺在深色地板上，正常赛道每一行的两侧
  一定有地板，只有十字/岔口那种横向大路面才会全白；弯道外侧永远是地板，所以这条对弯道零误伤。
- 它专门解决"路口太宽 → `wide + open` 超过画面 3/5 被否决掉"的情形（那条否决并保留着，
  否则摄像头被挡也会误判）。判据放在**所有否决之后**，与黑条判据同等否决权。
- 实现细节：俯视图里出界格点被填成白色，所以判全白之前先用 `IPM_Lut_Row()` 排掉含出界点的行，
  否则地平线附近的行会被误当成"全白"。

屏幕第 9 行（y=132）新增两个字段：`F` = 整行全白行数，`D` = 舵机当前实际占空比（460/440/474/418/500）。
上车时盯着 `D` 就能知道"现在到底在哪个档"，不用猜。

### 8.6 实车第六坑：左弯往右打（转向极性反了，已修）

现象：实车左弯时车往右打，几乎冲出去。

**根因不是舵机坏了，是两处符号错**：

| 位置 | 错的样子 | 后果 |
|---|---|---|
| `code/Pursuit_REMAIN.c` 的 `steer` | `steer = −(δ/δ_max)·RANGE_L` | 纯追踪接管时整条通路反向 |
| `code/Servo_REMAIN.h` 的档位宏 | `DUTY_L_SMALL = 440 / DUTY_R_SMALL = 474`（左右标反） | 分档打角整体反向 |

**实车极性真相**：占空比 **小 = 向右**，占空比 **大 = 向左**（中值 460，行程 395~534）。

三条互相独立的证据：

1. 仓库原注释就写着「偏大向左转，偏小向右转」；
2. 老 PD 通路 `Servo_Set_Turn()` 是 `duty = MID − out`，加纯追踪之前它在弯道上是能跟住的，
   说明「占空比变小」对应「往赛道外侧/偏右的方向修」；
3. 本次实车现象（左弯往右打）正好是上面两处符号错共同作用的结果。

改法：

```c
// code/Pursuit_REMAIN.c
steer = ((delta / PURSUIT_DELTA_MAX_DEG)) * ((float)SERVO_DUTY_RANGE_L);   // 去掉负号

// code/Servo_REMAIN.h
#define SERVO_DUTY_R_SMALL  (440)   // 向右 = 占空比减小
#define SERVO_DUTY_L_SMALL  (474)
#define SERVO_DUTY_R_BIG    (418)
#define SERVO_DUTY_L_BIG    (500)
```

现在三条通路（老 PD、连续纯追踪 `Servo_Set_Offset`、分档 `Servo_Set_Step`）统一约定：
**`out`/`demand` 正 = 向右 = 占空比减小**。`SERVO_DIR = −1` 就是这个约定的实现，
`SERVO_STEP_DIR = +1` 表示「正需求用 R 档（数值更小）」。

验证：屏幕第 9 行 `D` 显示实际占空比，左弯应看到 474 → 500，右弯 440 → 418，
直道/路口恒 460。若上电后 `Servo_Set_Duty(400)` 让前轮**向左**，说明这台车的舵机装反了，
把 `SERVO_DIR` 改 `+1`（三条通路一起翻，不用改档位宏）。

### 8.7 实车第七坑：急弯转不过来（加一档 + 缩前瞻 + 弯里更慢）

现象：极性修正后车能往正确方向打了，但**急弯打不动、转不过来**，车头被推着往外冲。

原因有三层，逐层加码：

| 层 | 原因 | 改法 |
|---|---|---|
| 1 | 最大档只有 418（−42 码），急弯需要 −60 以上 | 新增**超大档** 400 / 530（仍在 395~534 行程内） |
| 2 | 进大档阈值 6°，急弯要等到很晚才打满 | 大档阈值 6.00° → **3.50°**，退档 4.00° → 2.20° |
| 3 | 前瞻 800mm 太长，弯里算出来的 δ 偏小 | `PURSUIT_LD_MAX_MM` 800 → **700**、`PURSUIT_LD_MIN_MM` 250 → 220 |
| 4 | 弯里速度偏高，轮胎侧滑咬不住 | `PURSUIT_CURV_SLOW_K` 0.014 → **0.018** |

调档顺序（**一次只改一个，改完上车**）：

1. 还是转不过来 → `PURSUIT_LD_MAX_MM` 再降到 650，再不行 600；
2. 还是不够 → `SERVO_STEP_HUGE_IN` 从 10.0 降到 8.0（更早打满）；
3. 还在外冲 → 超大档步长再狠一点：400 → 397 / 530 → 533（**别再往下/往上顶，395 / 534 是机械极限**）；
4. 反过来开始画龙（弯里打过头）→ 把 `PURSUIT_CURV_SLOW_K` 加回 0.020 以上，或把超大档阈值抬回 12°。

屏幕判读：第 9 行 `D` 在急弯应出现 400（右）或 530（左）；如果急弯里 `D` 只到 418，说明需求根本没到 10°，
那就是前瞻太长（第 3 层），先动 `PURSUIT_LD_MAX_MM`。
