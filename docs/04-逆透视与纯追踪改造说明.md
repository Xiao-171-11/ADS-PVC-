## 0. 一句话总结

原来的控制链是「全局 Otsu → 逐行找边 → **一条最小二乘直线** → 全图加权平均中线 → 偏差 → 分段 Kp 打角」。
弯道上直线拟合会偏离真实边线，全图平均又把远场（真正的转向信息）和近场一起平均掉，所以**弯道只能靠"误差变大→多打角"事后追**，路口更是直接强行回正。

这一轮做了两件事：

1. **把图像逆透视成俯视图**（56×96，1 格 ≈ 6.7 mm × 11.8 mm），赛道在图上变成真正的「两条平行边线」，宽度、横向偏移、曲率都有了物理量纲；
2. **用纯追踪（Pure Pursuit）算转向**：在俯视图上按当前速度选一个前瞻点，用几何关系算出需要的转弯曲率 κ，再换算成前轮转角 δ 和舵机占空比——**这是"预瞄"，不是"追误差"**。

外加两个针对你特别提到的痛点做的专项保护：

- **十字路口四层判据**（互斥门 → 几何否决 → 状态机 → 出路口防重触发），过路口时**沿进路口前的航向直行**，绝不跟随横臂；
- **弯道不误判路口**、**冲出赛道检测**、**视野丢失时保持上一份控制量 5 帧**。

## 2. 逆透视（IPM）

### 2.1 为什么不用别人的标定矩阵

参考仓库（losehu/smartcar-C、wu58430/RUBO-UDIPM）里都是**硬编码一份 3×3 单应矩阵**，那是别人车、别人相机安装角标出来的。装到你车上必定错位。

所以这里的做法是：**用参数化的针孔模型自己生成查表**，把「相机高度 / 俯角 / 水平视场角」三个物理量变成宏，改宏就重新生成，不需要上位机、不需要标定板。

### 2.2 推导

车辆坐标系：**X 向右、Y 向前、Z 向上**，原点在车头正下方地面。相机装在 `(0, 0, h)`，光轴向下俯 `θ`。

相机坐标系三轴（相机 y 朝下、z 朝前）：

```
x_c = (1, 0, 0)
y_c = (0, -sinθ, -cosθ)
z_c = (0,  cosθ, -sinθ)
```

地面点 `P = (X, Y, 0)`，相对相机的向量 `P - C = (X, Y, -h)`，投影到相机坐标：

```
x_c = X
y_c = Y·(-sinθ) + (-h)·(-cosθ) = h·cosθ − Y·sinθ
z_c = Y·cosθ  + (-h)·(-sinθ)    = Y·cosθ + h·sinθ
```

针孔成像（像素坐标以像素中心为原点，`cx = W/2 − 0.5`、`cy = H/2 − 0.5`）：

```
u = cx + f · x_c / z_c
v = cy + f · y_c / z_c
f = (W/2) / tan(FOV_H / 2)
```

地平线（`Y → ∞`，此时 `v = cy − f·tanθ`）与 `z_c` 的正负决定了哪些像素是天空——天空行的查表项一律写 `IPM_LUT_INVALID`。

### 2.3 实测数值（v = 78.875 px、地平线 = 27.63 行）

`W=188, H=120, h=240 mm, θ=22°, FOV_H=100°`：

| 图像行 v | 对应地面 Y | 该处 1 像素 ≈ |
|---|---|---|
| 119（最下沿） | 144 mm | 2.8 mm |
| 110 | 170 mm | 3.5 mm |
| 100 | 207 mm | 4.6 mm |
| 90 | 256 mm | 7.0 mm |
| 80 | 324 mm | 11.5 mm |
| 70 | 423 mm | 20 mm |
| 60 | 583 mm | 35 mm |
| 50 | 888 mm | 70 mm |
| 40 | 1684 mm | 240 mm |

**结论：图像底行只覆盖 144 mm，图像 40 行以下已经是 1.7 m 开外、每像素 24 cm。**
所以俯视图取 `Y ∈ [150, 800] mm`——最下沿刚好不浪费，最远处 1 像素仍有 30 mm 分辨率。再远（>900 mm）单像素 45 mm 以上，边线宽度和噪声同量级，取进来只是噪声。

### 2.4 网格与查表

```c
IPM_H = 56, IPM_W = 96
Y_NEAR = 150 mm, Y_FAR = 800 mm, X_HALF = ±320 mm
→ DX = 6.74 mm / 格, DY = 11.82 mm / 格
→ 出界格点 38 / 5376 = 0.7%（越界填白，等于赛道两侧自动留白）
```

`IPM_Init()` 逐格算一次 `(u, v)`，存成 `uint16 ipm_lut[56][96]`（内容是 `v*188 + u` 的一维偏移，越界存 `0xFFFF`）。
运行时 `IPM_Process()` 只做 5376 次「读偏移 → 取像素 → 写目标」，**没有一次浮点运算**。

内存：LUT `56*96*2 = 10.5 KB`，俯视图 `56*96 = 5.25 KB`，合计 ≈ 15.8 KB。
（对比 losehu 用 `uint8*` 指针表 45.6 KB——同一个思路，这里用 `uint16` 偏移省了 3/4。）

> 相关宏：`IPM_CAM_HEIGHT_MM`、`IPM_CAM_PITCH_DEG`、`IPM_CAM_FOV_H_DEG`。改这三个值会重建整张表。`IPM_Init()` 末尾有自检：出界格点超过 1/4、或地平线跑出画面，就置 `ipm_info.ok = 0`，纯追踪自动退回老算法。

## 3. 纯追踪（Pure Pursuit）

### 3.1 找边线（`pursuit_extract_track`）

以画面中线 `47.5` 为起点，从最近一行（r=0）往最远行逐行扫：

- 从上一行的中线预测本行位置 `pred = pc + slope`（斜率跟踪弯道趋势）；
- 以 `pred` 为起点向左右各扫最多 `PURSUIT_SEARCH_COLS = 42` 格，遇到**第一段黑游程**就当作边线，取其游程中点；
- 游程宽度 > `PURSUIT_LINE_W_MAX = 8` 格 → 判定为**横向黑带（路口横臂）而不是边线**，丢弃；
- 两侧都找到、宽度落在 `[22, 92]` 格且与学习到的赛道宽度相差不到 50% → **可信行**，同时缓慢学习半宽和斜率；
- 只有一侧 → 用学习到的半宽推算另一侧，但推算点必须离预测位置不超过 10 格，否则降级为外推；
- 两侧都没有 → 沿预测方向外推（`center = pred`），**绝不去跟横向黑带**。

**这三条规则是仿真里踩出来的，缺一条就废**：

1. 必须**单格黑即命中**。曾经要求"连续 2 个黑点"，结果俯视图里近处边线只有 1 格宽（源图横向 8~12 mm/px 比格点 6.74 mm 还粗），近处 24 行全被判丢；
2. 游程扩展必须**双向**（`-1` 方向扩到 `a`、`+1` 方向扩到 `b`），两个方向都沿扫描方向扩会得到宽度恒为 1；
3. 扩展时索引必须夹 `0..IPM_W-1`。

### 3.2 前瞻距离随速度变化

```c
norm = control_base_speed_ref / CONTROL_SPEED_MAX      // 规划速度，不是实测速度
norm = clamp(norm, 0.30f, 1.0f)
Ld   = 250 + (800 - 250) * norm                        // 250 ~ 800 mm
r0   = (Ld - 150) / dy                                  // 换算成俯视图行号
```

`control_base_speed_ref` 必须是**第 6 步算出来的规划速度**，不能用编码器实测速度——否则「减速 → 前瞻变近 → 打角变大 → 更减速」会形成正反馈。

用规划速度还有一层好处：**减速和预瞄自动配套**。弯里慢下来 → 前瞻点自动拉近 → 打角更狠，正好符合"慢进快出"。

### 3.3 曲率 → 转角 → 舵机

目标点（对 `r0-1 / r0 / r0+1` 三行取平均，抑制单行噪声）：

```c
Xt = (cc - 47.5) * dx_mm          // 横向偏移，右为正
Yt = 150 + r0 * dy_mm             // 前向距离
κ  = 2·Xt / (Xt² + Yt²)           // 圆弧过原点和目标点的曲率
δ  = atan(κ · L)                  // 前轮转角，L = 130 mm 轴距
```

舵机（这一步的正负号最容易错，这里写清楚）：

```
Servo_Set_Offset() 里：out 正 = 向左打，最后 duty = Servo_MID − out
纯追踪里：δ 正 = 右转
所以：steer = −(δ / δ_max) · SERVO_DUTY_RANGE_L     // 取负号
     并按 [−RANGE_R, +RANGE_L] 非对称限幅（右 69 / 左 70）
```

仿真验证过符号：左弯 `κ<0 → δ<0 → steer>0 → duty 减小 → 向左` ✓；右弯反之 ✓。

### 3.4 差速与减速

```c
ratio = κ_use · REAR_TRACK / 2                        // 纯几何：内侧轮慢多少
      clamp ±CONTROL_DIFF_K_MAX (0.5)
slow  = 1 − 0.014 · |δ_deg|                           // 32° 满舵 → 0.55，再 clamp ≥ 0.42
```

`ratio` 与原来的 `CONTROL_DIFF_K * error` 同号（正 = 左轮快 = 右转），所以 `target_l = base·(1+ratio)`、`target_r = base·(1−ratio)` 这两行完全不用改。

原来的线性近似 `ratio = 0.004 × error` 是"像素偏差乘一个系数"，量纲说不清；现在是 `κ·轮距/2`，物理上就是内外轮的速度差比例。

## 4. 十字路口（四层判据）

这是本次的重点，按你提的"路口容易冲出去"专门设计。**判路口最难的不是"看出它是路口"，而是"别把弯道当路口"**。

### 第一层：互斥观测

俯视图里三种形态的统计量完全不同（下表是仿真实测值）：

| 场景 | 可信行 valid | 两侧同时丢 open | 单侧丢 one | 判据 |
|---|---|---|---|---|
| 直道居中 | 56 | 0 | 0 | — |
| 直道偏移 80 mm | 54 | 0 | 2 | 弯道 |
| 十字路口 | 21 | **35** | 0 | **路口** |
| 弯道 κ=1.5e-3 | 26 | 0 | **30** | **弯道** |
| 急弯 | 16 | 4 | **36** | 弯道 |
| 弯道上重叠路口 | 19 | 33 | 4 | 路口 |

→ **`open`（两侧同时丢）与 `one`（单侧丢）是一对互斥量：路口让 open 爆表，弯道让 one 爆表。**

### 第二层：互斥门（`pursuit_cross_update`）

```c
suspect = (open >= PURSUIT_CROSS_MIN_OPEN);            // 默认 6 行
/* 四条否决 —— 任一条成立就不判路口 */
open <= one * 3 / 2            // 单侧丢占主导 = 弯道
valid < PURSUIT_CROSS_MIN_VALID // 看得清的行太少，信息不可信
open > IPM_H * 3 / 5           // 一半以上都丢 = 摄像头/光照问题，不是路口
|κ_prev| > PURSUIT_CROSS_MAX_KAPPA   // 进路口前车头正在大转弯 = 这本来就是弯道
```

最后一条是关键：**急弯的 open 也可能到 4~6 行，但急弯的 κ 一定很大**，所以"进路口前一帧的曲率"是最好的否决条件（κ > 0.0025 即转弯半径 < 400 mm）。

### 第三层：状态机（IDLE → IN → OUT）

```c
连续 2 帧 suspect → 进入路口：cross_kappa = 进路口前的 κ，cross_ticks = 20
路口内：κ = cross_kappa × (cross_ticks / 20)     // 沿原航向直行，并逐帧衰减
        slow × CONTROL_CROSS_SPEED_SCALE (0.80)
退出：cross_ticks 归零（20 帧 = 0.4 s）或连续 4 帧干净
出路口后 cross_reject = 20 帧禁止再判 —— 防"刚出路口又判路口"来回抖
```

**过路口为什么"沿原航向直行"而不是"回正"**：进路口那一刻车头的航向就是赛道的方向。保持 κ 衰减到 0 等于让车沿一条直线穿过路口；而回正（`error = 0`）等于强行把车头掰向画面中心——如果车是斜着进路口的，掰正就是往路口对角冲，这正是原来 MIDLine 里那个 `midline_info.error = 0.0f; return` 的后果。

所以 `code\MIDLine_REMAIN.c` 的路口分支也一起改成了"保持上一帧中线"：

```c
midline_info.center         = midline_info.last_mid_line;
midline_info.mid_line_value = (uint8)(midline_info.last_mid_line + 0.5f);
midline_info.error          = midline_info.last_mid_line - (MT9V03X_W * 0.5f);
```

### 第四层：物理保护

路口内即使判错，后果也被限制：限速到 80%、`Servo_Set_Offset()` 里有 `SERVO_SLEW_MAX = 14`（每 5 ms 最多变 14 个占空比，69 打满要约 25 ms），舵机不会因为一次误判瞬间甩到极限。

## 5. 冲出赛道保护

```c
near_off = (最近 6 行中线平均 − 47.5) × dx_mm      // 车头相对赛道中心的横向偏移
if (|near_off| > 190 mm && |near_off| < 570 mm)     // 190 = 半赛道宽 225 的安全余量
{
    off_track = 1;
    steer     = (−near_off) × 0.22;                // 直接朝赛道中心打
    slow     ×= CONTROL_OFFTRACK_SPEED_SCALE (0.45)
}
```

上限 570 mm 是为了排除"整幅图都找不到线"的极端情况（那时候 `near_off` 没有意义）。

## 6. 视野丢失时保持 5 帧（防止弯中抖动）

```c
if (trk_valid < PURSUIT_CROSS_MIN_VALID)      // 可信行 < 8
{
    if (pursuit_hold < PURSUIT_HOLD_FRAMES)   // 5 帧 = 100 ms
    {
        pursuit_hold ++;
        snap = 上一份快照;                     // 原样继续用，只更新统计字段
        发布并返回;
    }
}
else pursuit_hold = 0;
```

没有这一段的话，一帧反光/抖动就会让 `valid` 变成 0，控制权瞬间交给老的分段 Kp 控制器——两套控制器输出差得远，车就会在弯中"抖一下"。这也是纯追踪必须配的东西：**两套算法的切换必须是"渐进的"或"有滞回的"，不能逐帧硬切。**

`Servo_Set_Turn()` 里也加了对应的无扰切换：从纯追踪切回偏差打角时，先把 `servo_err_f` 和 `servo_last_error` 同步成当前误差，否则微分项 `SERVO_KD * (error − last_error)` 会猛跳一下。

## 7. 上车标定步骤（按顺序做，每步都要看屏幕）

TFT180 上的新字段（第 7 行 `y=100`、第 8 行 `y=116`；屏幕是默认竖屏 **128×160**、字体 **8×16**）：

| 字段 | 位置 | 含义 | 正常情况下应该看到 |
|---|---|---|---|
| `P` | 第 7 行 x=0 | `valid_rows` 可信行数 | 直道 **50~56**；弯道 26~40；路口 < 25 |
| `c` | 第 7 行 x=32 | `cross` 路口标志 | 直道/弯道 **0**，压到路口 1~2 帧内变 1 |
| `d` | 第 7 行 x=56 | `delta_deg` 前轮转角 | 直道 ≈ 0，弯道 5~20，满舵 ≤ 32 |
| `o` | 第 7 行 x=104 | `off_track` | 正常 **0** |
| `k` | 第 8 行 x=0 | 曲率 ×1000 | 直道 ≈ 0，弯道 ±0.8~2.5 |
| `L` | 第 8 行 x=48 | `lookahead_mm` 前瞻距离 | 40 速 ≈ 250~400 mm，75 速 ≈ 617 mm |

> **排版铁律**：逐飞 `tft180_show_int(x,y,dat,num)` 的渲染长度是**定长 `num+1`**，`tft180_show_float(x,y,dat,num,pointnum)` 是**定长 `num+pointnum+2`**（不足补空格）。每个字符占 8 像素（8X16 字体），所以 `x + 8×(长度-1) + 8 ≤ 128` 必须成立，否则 `tft180_show_char` 会在 `zf_device_tft180.c:460` 触发 `zf_assert(x < tft180_width_max)` 死机（见 §8.2）。

**第 1 步：验证逆透视本身**

把 `code\IPM_REMAIN.h` 里 `IPM_DIS_EN` 改成 `1`，重新编译。屏幕上会直接显示 96×56 的俯视图（画在竖屏最下面 `y=104~159`，不盖住上面六行文字；此模式下第 7/8 行的 `P/c/d/o/k/L` 会自动让位不画）。

- 车摆在直道正中：俯视图应该是**两条竖直等宽的边界**，左右对称，赛道宽度约占画面 67 格（450 mm / 6.74 mm）；
- 如果两条边界是**斜的**：`IPM_CAM_PITCH_DEG` 不对（斜向同侧 = 相机装歪了，用 `SERVO_TRIM` 式的机械垫片解决，或者给 u 加一个角度补偿）；
- 如果赛道只露出下半部分、上半部分是白的：`IPM_Y_FAR_MM` 太大（相机看到的地面没到 800 mm），改小；
- 如果近处赛道被切掉：`IPM_Y_NEAR_MM` 太大，改小到 130。

**第 2 步：量轴距和轮距**

`PURSUIT_WHEELBASE_MM`（前后轴中心距，默认 130）和 `PURSUIT_REAR_TRACK_MM`（左右轮中心距，默认 120）用尺子量。这两个值决定 `δ` 和差速比例的绝对正确性。

**第 3 步：确认舵机行程与打角极性**

舵机实测：中值 **464**、50 Hz、可用占空比 **395 ~ 534**。这三个数已经写进 `code\Servo_REMAIN.h`：

```c
#define Servo_MID      (464)
#define SERVO_DUTY_MIN (395)     // 机械下限，谁也不许越过
#define SERVO_DUTY_MAX (534)     // 机械上限
#define SERVO_DIR      (-1)      // 打角极性，见下
```

- `SERVO_DUTY_MIN/MAX` 是**唯一**的行程来源：`Servo_Set_Duty()` 直接夹这两个数，`SERVO_DUTY_RANGE_L/R` 也由它们推导（向下 69 个码、向上 70 个码）。所以偏差 PD、纯追踪、出弯保持三条路径**都不可能**把占空比推出 395~534，不存在"某条通路忘了限幅"的情况。
- **打角极性标定**（必做，5 秒）：上电、车轮离地，临时在 `Servo_Init()` 末尾加 `Servo_Set_Duty(400);` 看前轮往哪边偏，再改成 `Servo_Set_Duty(530);` 看另一边。
  - 若 **400 偏左、530 偏右** → 把 `SERVO_DIR` 改成 `(+1)`；
  - 若 **400 偏右、530 偏左** → 保持 `SERVO_DIR (-1)`（仓库原有方向）。
  这个符号同时作用于偏差通路与纯追踪通路，改一处两条一起翻，不会出现"一条通路反、一条正"的错位。**不要**再用 `SERVO_REVERSE` 调极性——它只翻偏差通路。
- 然后把 `PURSUIT_DELTA_MAX_DEG` 改成实测的**最大前轮转角**（打死方向，量角器或几何测量）。它必须和 `SERVO_DUTY_RANGE_L`（默认 69 个码）对应同一物理极限，否则 `δ` 与占空比不成比例——**这一条最容易忘，也最影响手感**。

**第 4 步：低速试跑**

`CONTROL_BASE_SPEED` 先降到 **40**，`CONTROL_SPEED_MAX` 降到 **60**（保证 `norm` 在前瞻距离的中段）。
看 `P` 是否稳定在 40 以上、`κ×1000` 是否在直道上抖动（抖动 > ±0.3 说明提取器抓到了横臂或反光，调 `PURSUIT_LINE_W_MAX` 或提高 Otsu 阈值下限）。

**第 5 步：逐项加压**

1. 先跑直道 → 确认 `d` ≈ 0，车不蛇行；
2. 再跑单弯 → 确认 `c` 始终为 0（**弯道不许判成路口**）；
3. 再跑十字 → 确认 `c` 变成 1 后车是"直穿"而不是"拐弯"；
4. 最后加环岛/斑马线 → 斑马线原来那套 `Zebra_REMAIN` 起停逻辑不受影响（它只看 `base_image`）。

### 8.1 首次编译踩到的坑：头文件循环 include（已修）

ADS 报 `Pursuit_REMAIN.h 97/33 undeclared identifier "IPM_H"` / `expression must be constant`，根因不是漏写宏，而是**本工程头文件的组织方式**：

```
IPM_REMAIN.c
 └─ #include "IPM_REMAIN.h"      ← 守卫 CODE_IPM_REMAIN_H_ 置位
     └─ #include "zf_common_headfile.h"
         └─ 用户层 … → #include "IPM_REMAIN.h"   ← 守卫已置位，整个文件被跳过（宏还没定义！）
                     → #include "Pursuit_REMAIN.h"
                         └─ extern int16 pursuit_center_row[IPM_H];   ← IPM_H 还不存在 → 报错
```

也就是说：**任何用户层头文件里，只要用到"排在自己后面"的头文件定义的宏，就会踩这个坑**（而单独编译那个头文件的 .c 时反而正常，所以肉眼看代码看不出来）。

修法：`Pursuit_REMAIN.h` 里的 `extern int16 pursuit_center_row[IPM_H];` 改成 `extern int16 pursuit_center_row[];`（不完整数组类型的 extern 声明合法，定义处仍是 `[IPM_H]`，链接期一致），从此两个头文件之间没有宏依赖。

**以后写新头文件的规矩**：头文件里只用「本文件自己 `#define` 的宏」+「`zf_common_*` / 驱动层符号」，不要用别的用户层头文件的宏；确实要共享常量，就写进那个宏所属的头文件，或者用 `[]` / 显式长度。

### 8.2 实车第二坑：屏幕 assert 在 `zf_device_tft180.c:460`（已修）

实车屏幕上打出：

```
Assert error
file: zf_device/
zf_device_tft180.c
line: 460
```

`zf_device_tft180.c:460` 是 `tft180_show_char()` 里的 `zf_assert(x < tft180_width_max);`——**x 越界**，不是数据错。

根因：原 `Pursuit_Show_On_TFT180()` 写了 `tft180_show_float(96, CAMERA_INFO_Y2, kappa*1000, 1, 2)`。逐飞这个函数**不按实际数字长度渲染**，而是先把缓冲区按定长补满空格：

```c
memset(data_buffer, 0, 17);
memset(data_buffer, ' ', num + pointnum + 2);   // 定长：1 + 2 + 2 = 5 个字符
func_double_to_str(data_buffer, dat_temp, pointnum);   // 只覆写前几位，末尾空格不写 NUL
tft180_show_string(x, y, data_buffer);                 // strlen = 5，而不是数字的真实长度
```

也就是 `strlen` 恒等于 `num + pointnum + 2 = 5`（`func_double_to_str` 不在数字末尾补 NUL，尾部空格被一起画出来）。屏幕是默认竖屏 **128 宽**（`tft180_set_dir(TFT180_PORTAIT)` → `tft180_width_max=128`）、字体 **8×16**，于是 5 个字符的落点是 `96 / 104 / 112 / 120 / 128`——**最后一个字符起点正好 128**，`show_char` 内部断言 `x < 128` 直接失败。因为长度是定长补齐的，**跟数值大小无关，第一帧必死**，所以表现成"上电就停在 assert 画面"。

（`tft180_show_int(x,y,dat,num)` 同理：`memset(data_buffer,' ',num+1)` + `func_int_to_str` 不补 NUL ⇒ `strlen` 恒为 `num+1`。）

修法（三处）：

1. `Pursuit_Show_On_TFT180()` 整体重排：位置改到第 7/8 行（`y = CAMERA_INFO_TOP + 100 / +116`），所有字段按 `num`/`pointnum` 的实际定长留格子（最右到 `x=127`），并加 `if((y + 16) > tft180_height_max) return;` 的兜底；
2. `IPM_Show_On_TFT180()` 从 `(0,0)` 改成**底对齐** `(0, tft180_height_max - IPM_H)`（96×56 落在 `y=104~159`），不再盖住上面六行；
3. 新增编译开关 `PURSUIT_DIS_EN`；`IPM_DIS_EN=1` 时第 7/8 行自动让位（`#if ((1 == PURSUIT_DIS_EN) && (0 == IPM_DIS_EN))`）。

**通用教训（本工程后续加任何屏幕输出都要遵守）**：

| 函数 | 渲染长度（字符数） |
|---|---|
| `tft180_show_string(x,y,str)` | `strlen(str)` |
| `tft180_show_int(x,y,dat,num)` | 定长 `num + 1` |
| `tft180_show_float(x,y,dat,num,pointnum)` | 定长 `num + pointnum + 2` |

必须满足 `x + 8 × 长度 ≤ 128`（竖屏 8×16 字体）；横屏（`TFT180_CROSSWISE`）是 160 宽、128 高，`y + 16 ≤ 128`。
